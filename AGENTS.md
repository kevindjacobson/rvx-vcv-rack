# RVX — project instructions

- Use RVX as the project and plugin-suite name and `rvx-vcv-rack` as the repository name and directory. Preserve the actual names of referenced LZX products, VCV Rack, and third-party projects.
- Planning and research remain active. Begin plugin implementation, scaffolding, prototype builds, or dependency installation only within a scope the user has explicitly approved. Approval for that scope persists and must not be requested again; it does not approve broader release or fidelity work. Creating and maintaining this repository and its planning documents is authorized.
- The user prefers close reproduction of LZX controls, ports and behavior, with analog video signal behavior preserved wherever practical. Record approximation limits explicitly.
- Mac and bidirectional Syphon are required. Syphon selection should feel familiar to users of Rack audio device selection. Do not postpone Syphon beyond the first usable release.
- Preserve Memory Palace and dirty NTSC mixing as explicit requirements. Do not substitute a generic feedback or VHS effect without identifying the differences.
- Keep README.md limited to installation, quick start and a table of all modules. Put project history, research context and decisions in PROJECT.md or VCV-Video-System-Plan.md.
- Read README.md, PROJECT.md and VCV-Video-System-Plan.md before substantial work. Treat proposed decisions and untested acceptance gates as proposals, not verified implementation facts.
- Keep source citations, functional feasibility grades and fidelity claims distinct. The existing grades are engineering estimates, not measurements or promises of circuit equivalence.
- Follow ENGINEERING.md: audit all open issues before work, before PR readiness/merge and after every merge; reconcile changed assumptions, evidence, acceptance criteria and dependencies. Record the reviewed revisions and outcomes in the issue/PR. Treat unmerged proposals and unresolved questions accurately.
- Treat source code as a deliverable alongside product behavior. Review readability, shared contracts, reusable operators, testability, ownership/threading, performance and maintainability. Preserve module-specific fidelity and avoid speculative abstractions. Apply the same standard when writing implementation specifications.
- Use a separate branch and Git worktree for each active issue, and run independent issues in parallel where practical after checking dependencies and shared contracts. Workers own their assigned worktree/files; do not share mutable checkouts or overwrite another worker's changes.
- Always spawn a fresh independent reviewer with `fork_turns: "none"` before PR readiness. Give requirements, exact revisions, repository/diff access and validation evidence without the author's chat or self-assessment. The reviewer must not be the writer; substantive fixes require another fresh review. Record findings and resolutions in the PR.
- Use Ultra for orchestration. Cheaper models and lower effort may handle routine, well-specified writing tasks; escalate capability/effort when the work requires it. Preserve the same quality and review criteria for all workers.
- LZX-Mac-Feasibility.md is generated by research/build_report.py. Update both its source text and the generated report when changing that assessment.
- Keep downloaded page caches out of Git. Do not publish a remote repository or contact external authors unless the user requests it.
- At the natural end of substantial work, consider whether there is reusable knowledge worth a Codex skill. Recommend a skill only when useful; keep project-specific decisions in these documents. Create a skill only when requested.
