# Rack 2.6.6 adapter evidence

The RVX prototype derives its video graph from Rack's native cable UI on Rack's UI thread. It calls the public `RackWidget::getCompleteCables()` API and immediately converts each complete cable's public `inputPort` and `outputPort` endpoints into RVX node keys, typed port indices and separately shared-owned node state. No `CableWidget`, `PortWidget`, Rack `Module`, Rack `Cable`, texture pointer or other Rack-owned pointer is stored in the submitted graph or used by the video worker.

This decision was checked against VCV Rack tag `v2.6.6`, commit `061ccf63c1758599396ac1bb10d47345d9d34076`:

- [`RackWidget.hpp`](https://github.com/VCVRack/Rack/blob/061ccf63c1758599396ac1bb10d47345d9d34076/include/app/RackWidget.hpp) exposes `getCompleteCables()` and the cable collection methods without Rack's `PRIVATE` marker.
- [`CableWidget.hpp`](https://github.com/VCVRack/Rack/blob/061ccf63c1758599396ac1bb10d47345d9d34076/include/app/CableWidget.hpp) exposes `inputPort`, `outputPort` and `isComplete()`. RVX uses its own `PortWidget` subclass as endpoint metadata and does not dereference the widget outside the synchronous UI scan.
- [`CableWidget.cpp`](https://github.com/VCVRack/Rack/blob/061ccf63c1758599396ac1bb10d47345d9d34076/src/app/CableWidget.cpp) creates/removes the engine cable when a UI cable becomes complete/incomplete. [`PortWidget.cpp`](https://github.com/VCVRack/Rack/blob/061ccf63c1758599396ac1bb10d47345d9d34076/src/app/PortWidget.cpp) removes incomplete drag cables and uses the same native widgets for undo/redo actions.
- [`Widget.cpp`](https://github.com/VCVRack/Rack/blob/061ccf63c1758599396ac1bb10d47345d9d34076/src/widget/Widget.cpp) calls `step()` for children regardless of visibility or draw clipping. [`Window.cpp`](https://github.com/VCVRack/Rack/blob/061ccf63c1758599396ac1bb10d47345d9d34076/src/window/Window.cpp) calls `scene->step()` before testing whether the GLFW window is visible or iconified. An RVX module widget therefore continues topology synchronization when it is offscreen or Rack is minimized. Video timing does not use these UI steps; the independently owned RVX engine continues its own clock with the last immutable graph.
- [`Engine.cpp`](https://github.com/VCVRack/Rack/blob/061ccf63c1758599396ac1bb10d47345d9d34076/src/engine/Engine.cpp) locks its engine mutex during cable add/remove and calls `Module::onPortChange()` before releasing that lock. RVX's callback stores an atomic topology hint; CV Bridge also advances its capture epoch/reset counters on audio-input connection changes. It never queries Rack, allocates frames or stops a worker there. The topology callback is only a hint because Rack does not emit it for every stacked output cable change.
- The same engine source shows why `getCableIds()` followed by `getCable()` is unsuitable for RVX: each call manages its own lock, and `getCable()` returns a mutable pointer after its read lock has been released. `Engine::toJson()` does copy cable metadata under a read lock, but also serializes every module and allocates a full patch JSON tree, making it inappropriate for topology polling.
- [`patch.cpp`](https://github.com/VCVRack/Rack/blob/061ccf63c1758599396ac1bb10d47345d9d34076/src/patch.cpp) loads the engine JSON before constructing rack widgets. The first RVX widget step therefore observes the final native cable widget set after patch load. Rack's own cable JSON remains the sole serialized topology; RVX derives its graph and does not duplicate cable state in module JSON.
- [`Module.cpp`](https://github.com/VCVRack/Rack/blob/061ccf63c1758599396ac1bb10d47345d9d34076/src/engine/Module.cpp) restores native parameters and bypass before optional module data. RVX mirrors that completed native state after the base `fromJson()` call.

Every RVX module can initiate one scan per Rack UI frame, while the context service suppresses duplicate scans using `Window::getFrameTime()` and submits only when its canonical node/edge set changes. This avoids assigning graph or clock ownership to the monitor. Incomplete drag cables are excluded. A stock Rack output patched into an RVX video input becomes an explicit invalid edge with source key zero, allowing the renderer to report the error and provide empty input. An RVX video output patched into a stock Rack input has no video consumer, and its native voltage remains zero. The UI adapter separately counts each such outgoing cable by source node, updates its diagnostic revision even when the render graph is unchanged, and displays the warning on the originating RVX panel. This value-only diagnostic never leaves the UI/service boundary.

Services are indexed by the current Rack `Engine*` only at the UI/lifecycle boundary; each context receives its own RVX engine. Node keys are process-unique and never reused. Submitted graphs retain `shared_ptr<Node>` state, so an in-flight render remains memory-safe after a Rack module is deleted. `onRemove()` unregisters without joining. When the last node leaves a context, a registry-owned cleanup thread stops and destroys that context service outside Rack's engine lock. The registry owns no video resources itself and removes the context entry immediately.

The lifecycle registry also reserves automatic Video I/O publisher names across live RVX modules. A recalled automatic name is reserved during `onAdd()` before a newly created module selects the first free `RVX` suffix; duplication receives a new suffix, and deletion or user rename releases the former automatic name. Explicit publisher names remain unchanged, including duplicates, and a duplicate is reported on the Video I/O panel.

Rack audio frame or sample-rate discontinuities start a new capture epoch only for CV Bridge. Audio-input cable transitions and queue-loss bursts also start a fresh capture epoch, preventing interpolation across missing captures. They do not reset Test Image phase, received source video, or Frame Delay history. Module reset and patch-state load remain explicit video resets, and Frame Delay's Clear control resets its history.

Rack restores native parameters and its internal bypass flag before invoking a module's `dataFromJson()`, and it skips that callback when the JSON has no `data` object. RVX therefore wraps native `Module::fromJson()` and mirrors parameters and bypass into shared render state before publishing the reset. This covers initial patch load, presets, paste, and history restoration without waiting for an audio callback.

## Diagnostic statistics

Set `RVX_DIAGNOSTICS=1` before launching Rack to emit at most one status line per second plus changed topology revisions. Each status line identifies the video worker run and reports every completed render in that run as `renderFrames`. That count is the denominator for p50/p95/p99 render time and `renderDeadlineMisses`; skipped scheduled ticks have no render sample and are reported separately as `skippedTicks`. The retained `lateFrames` API field is logged as `lateTickSlots` and equals rendered deadline misses plus skipped ticks.

Timing uses a fixed 0.05 ms histogram with a 100 ms saturation bucket and nearest-rank quantiles, returned as bucket upper bounds. `histogramSaturated` identifies samples whose quantiles were capped; `maxMs` remains the exact observed maximum. `renderErrors` is the sum of renderer-reported error events, while `renderErrorFrames` counts completed renders that reported at least one error. Adapter cable errors remain separate as `adapterErrors`.

Statistics reset when an `Engine` video worker starts and remain available after it stops. `workerRun` increments at each start, so results from backend/context restarts are not combined. Graph/topology revisions within a running worker do not reset statistics; a native stress result must therefore report its worker run and should use one uninterrupted run for its measurement interval. Collection happens only on the video worker after each render, uses fixed storage, and does not add work to Rack's audio callback. Status lines also include current frame bytes, graph node/edge counts, and latest monitor/source sequence. The opt-in log contains no Syphon identities, publisher names, paths or credentials.
